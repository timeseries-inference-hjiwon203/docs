# 과제 1 데이터 수집 보고

작성: 2026-10-21 · 대상 보드: aip-1 (Jetson Orin Nano) · 저장 버킷: aip-1 InfluxDB `jiwon`

## 1. 수집 방식

- **원본**: 운영진 InfluxDB(OSS v2.7.12) `iot-bucket`. 접속 주소는 `https://influx.java21.net` (와이파이 기준).
- **가져오는 것**: 장소 `실습실`, `회의실` × 항목 `co2`, `temperature`, `humidity`, 모든 센서(device_id).
- **방법**: 파이썬 스크립트 `sync.py`(표준 라이브러리만 사용)를 systemd timer가 1분마다 실행한다.
  - 마지막으로 복사한 시각을 `state.json`에 저장하고, 다음 실행은 그 시각 30분 전부터 다시 읽는다.
  - 같은 (항목, 태그, 시각)의 점은 InfluxDB가 덮어쓰므로, 겹쳐 읽어도 중복이 생기지 않는다.
  - 읽기·쓰기에 실패하면 `state.json`을 그대로 두고 끝낸다. 다음 실행이 같은 지점부터 다시 시도한다.
- **설정**: `config.json`에 원본/대상 주소, 장소, 항목 이름 매핑, 태그를 둔다. 토큰은 `.env`(권한 600)에만 둔다.
- **왜 MQTT 수집기 대신 DB 복사인가**: 같은 센서 데이터가 운영진 DB에 2025-08-08부터 이미 쌓여 있어, 1년 넘는 과거 데이터를 바로 학습에 쓸 수 있다.

## 2. 과거 데이터 채우기 (backfill)

- 기간: 2025-08-08 ~ 2026-10-21 06:34 UTC, 하루 단위로 나눠 복사.
- 하루 건수: 2025-09 무렵 약 9,500건 → 2026-10 무렵 약 19,000건 (2026-08에 실습실 습도·온도 센서가 늘어남).
- **원본에도 없는 구간**: 2025-08-15 ~ 2025-09-02 (0건). 운영진 DB 자체에 이 기간 값이 없다.

| 발견 | 처리 |

| 2025-09-03 이전에는 `device_id` 태그가 없음 | 그대로 저장. 분석 때 주의 |

| `rssi`, `snr` 등은 게이트웨이 2대가 각각 기록(`gateway_id`) | 수집 대상 아님. co2·온도·습도에는 `gateway_id`가 없어 중복 없음 |

## 4. 수집 현황 (2026-10-21 16:00 KST, 최근 24시간, `status.py`)

커버율 칸 = 센서의 보고 주기(중앙값) × 2. 30분 이상 빈 구간: 없음.

| 장소 | 센서 수 (co2 / 습도 / 온도) | 보고 주기 | 커버율 |
|---|---|---|---|
| 실습실 | 4 / 8 / 8 | 1분, 2분, 10분 섞임 | 98.6% ~ 100.0% |
| 회의실 | 1 / 1 / 1 | 10분 | 98.6% |

처음에는 실습실 전체를 5분 칸으로 계산해서 10분 주기 센서 2개가 49.8%로 나왔다. 데이터가 빠진 게 아니라 칸이 보고 주기보다 작았기 때문이라, 센서별 주기에 맞춰 칸 크기를 정하도록 바꿨다.

## 5. 장애 시험

### 시험 1: 원본 DB에 연결할 수 없을 때 (SC-001) — 통과

`config.json`의 원본 주소를 존재하지 않는 주소로 바꿔 연결 실패를 흉내 냈다가 되돌렸다.

```
16:03:38 2026-10-21T06:32:38Z ~ 07:03:38Z: 412건 (정상)
16:04:38 실패 2026-10-21T06:33:38Z ~ 07:04:38Z: <urlopen error [Errno -2] Name or service not known>
16:05:39 Failed to start jiwon-collector.service (실패, 다음 실행 대기)
16:06:39 2026-10-21T06:33:38Z ~ 07:06:39Z: 434건 (주소 복구 후 첫 실행)
```

- 실패하는 동안 프로그램은 멈추지 않고 실패만 기록했다.
- 복구 후 첫 실행(1분 이내)이 실패 전 지점(06:33:38Z)부터 끊긴 시간까지 한 번에 다시 가져왔다.

### 시험 2: 보드 재부팅 (SC-002) — 통과

`sudo reboot` 뒤 로그인하거나 명령을 실행하지 않고 기다렸다.

```
16:17:05 Finished jiwon-collector.service (재부팅 전 마지막 실행)
16:17:56 sudo reboot
-- Boot f4cf92714fd74b9e84ec49f5b04bcff9 --
16:19:26 2026-10-21T06:47:05Z ~ 07:19:26Z: 437건 (재부팅 후 첫 실행)
16:19:26 Finished jiwon-collector.service
```

- 부팅 1분 뒤 timer가 수집을 자동으로 시작했다.
- 재부팅 동안 빈 약 2분도 첫 실행이 함께 가져와서 빠진 값이 없다.

## 6. 형식 변경 대응 (SC-004) — 통과

가정: 원본에 새 센서 항목(기압 `pressure`)이 추가되어 함께 수집해야 한다.

바꾼 것: `config.json`의 `measurements`에 한 줄 추가. 코드(`sync.py`)는 그대로.

```json
"measurements": { "co2": "co2", "temperature": "temperature", "humidity": "humidity", "pressure": "pressure" }
```

결과(`sync.py --dry-run`, 2026-10-21 16:11 KST):

```
2026-10-21T06:41:23Z ~ 07:11:23Z: 465건 (실습실/co2=64, 실습실/humidity=164, 실습실/pressure=64, 실습실/temperature=164, 회의실/co2=3, 회의실/humidity=3, 회의실/temperature=3)
```

- 설정 한 줄만으로 `실습실/pressure=64`건이 새로 잡혔다.
- 항목 이름이 바뀌는 경우(예: `co2` → `CO2_ppm`)도 같은 방식이다. `"CO2_ppm": "co2"`를 추가하면 내 DB에는 계속 `co2`로 이어서 쌓인다.
- 시험 뒤 설정은 원래대로 되돌렸다(수집 대상은 co2·온도·습도 유지).

## 7. 심화(B)

### B-1. 같은 값이 여러 번 와도 중복 없이 저장 (T018) — 일부 확인

수집기는 매분 최근 30분을 다시 읽어 다시 쓴다. 같은 값을 약 30번 쓰는 셈이지만, InfluxDB는 (항목, 태그, 시각)이 같은 점을 새로 추가하지 않고 덮어쓴다. 재전송·재시도로 같은 값이 다시 와도 같은 방식으로 중복이 생기지 않는다.

남은 것: 원본 DB 쪽에서 같은 장치·항목 값이 몇 ms 차이로 두 번 기록된 경우(앞서 약 2ms 간격 재전송을 본 적 있음)는 시각이 달라 덮어쓰기로 합쳐지지 않는다. 이런 값을 찾아내 처리하는 일은 아직 하지 않았다.

증거(`verify.py 2026-10-20`, UTC 하루):

|---|---|---:|---:|---|
| 실습실 | co2 | 3,211 | 3,211 | 같음 |
| 실습실 | humidity | 7,897 | 7,897 | 같음 |
| 실습실 | temperature | 7,896 | 7,896 | 같음 |

### B-2. 1년 뒤 저장 용량과 보관 정책 (T017)

**측정 (2026-10-21)**

- 디스크: `/var/lib/influxdb` 27MB (서현 버킷·메타데이터 포함이라 실제보다 약간 크게 잡힌 값)
- 내 버킷 전체: 4,175,874건 (2025-08-08 ~ 2026-10-21, `verify.py --total`)
- 값 1개당 약 **6.8바이트**. InfluxDB가 일정 간격 시각과 비슷한 값을 압축하기 때문에 작다.

**1년 뒤 추정**

- 현재 하루 약 19,400건 (2026-10-20 실측 19,427건)
- 1년 = 19,400 × 365 ≈ 708만 건 × 6.8바이트 ≈ **약 48MB/년**
- 센서 수가 2배로 늘어도 약 100MB/년. aip-1 SD카드 여유 공간(약 88GB)에 비하면 매우 작다.

**보관 정책 (설계)**

| 데이터 | 보관 기간 | 이유 |
|---|---|---|
| 원본(1~10분 간격) | 무기한 (최소 학습·평가 기간 동안) | 용량 부담이 거의 없고, 과제 2~8 학습에 원본이 필요 |
| 5분 평균 (별도 버킷, InfluxDB task로 매시간 생성) | 무기한 | 학습 데이터 조회가 빨라짐. 1년 치 전체 건수를 한 번에 세는 데 60초를 넘길 만큼 원본 조회가 느렸다 |
| 원본 보관 기간을 줄이는 경우 | 예: 1년 뒤 원본 180일 | 센서가 크게 늘거나 SD카드 공간이 부족해질 때만 적용 |

- 지금은 설계만 하고 삭제·보관 기간 설정은 적용하지 않는다(1년 치 원본을 학습에 쓰기 때문).
- 참고: 매분 30분을 겹쳐 다시 쓰므로 실제 쓰기 양은 새 데이터의 약 30배다. 겹쳐 읽는 이유는 측정 시각보다 늦게 원본 DB에 들어오는 값을 놓치지 않기 위해서다(센서 보고 주기와는 무관). 이 지연을 원본 DB에서 직접 잴 수 없어 30분으로 넉넉하게 두었다. 1년 약 48MB 수준이라 SD카드 부담이 작아 그대로 유지한다. 지연이 짧다는 근거가 생기면 `config.json`의 `overlap_minutes`만 줄이면 된다.
