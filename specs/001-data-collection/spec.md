# Feature Specification: 데이터 수집 체계 (과제 1)

**Feature Branch**: `001-data-collection`

**Created**: 2026-10-20

**Status**: Draft

**Input**: 과제 안내문 "과제 1. 데이터 수집 체계" — MQTT로 1분마다 들어오는 CO₂·온도·습도 메시지를 받아
공간·항목·시각별로 저장하는 수집기를 Jetson에서 상시 가동한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 센서 메시지를 받아 저장한다 (Priority: P1) 🎯 MVP

수집기를 실행하면, MQTT 브로커에서 들어오는 센서 메시지가 공간·항목·시각별로 시계열 저장소에 쌓인다.

**Why this priority**: 데이터가 없으면 과제 2~8 모두 시작할 수 없다.

**Independent Test**: 수집기를 10분 돌린 뒤 저장소를 조회해, 4개 공간 × 3개 항목에 1분 간격으로 값이 쌓였는지 본다.

**Acceptance Scenarios**:

1. **Given** 브로커가 메시지를 보내는 중, **When** 수집기를 실행하면, **Then** 1분 안에 저장소에 첫 값이 보인다.

---

### User Story 2 - 사람 손 없이 다시 살아난다 (Priority: P1)

브로커가 재시작되거나 네트워크가 끊기거나 보드가 재부팅돼도 수집이 자동으로 다시 시작된다.

**Why this priority**: 하루만 멈춰도 그날 데이터는 학습·평가에 못 쓴다.

**Independent Test**: 수집 중 브로커를 끊었다 다시 연결하고, 보드를 재부팅한 뒤 수집이 재개되는지 본다.

**Acceptance Scenarios**:

1. **Given** 수집 중, **When** 브로커를 껐다 켜면, **Then** 1분 안에 수집이 다시 시작된다.
2. **Given** 수집기가 등록된 보드, **When** 재부팅하면, **Then** 로그인 없이 수집이 자동으로 시작된다.

---

### User Story 3 - 수집 현황을 한눈에 본다 (Priority: P2)

"지금 데이터가 잘 쌓이고 있는가"를 확인한다.

**Why this priority**: 멈춘 것을 빨리 알아야 고칠 수 있고, 커버율 보고가 산출물이다.

**Independent Test**: 공간·항목별 건수, 마지막 수신 시각, 24시간 커버율이 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 24시간 수집된 데이터, **When** 현황을 조회하면, **Then** 공간·항목별 커버율(1분 칸 중 값이 있는 비율)이 표로 나온다.
2. **Given** 빠진 구간, **When** 현황을 조회하면, **Then** 결측 구간의 시작·끝 시각을 알 수 있다.

---

### User Story 4 - 형식이 바뀌어도 설정만 고친다 (Priority: P2)

메시지 형식이 바뀌거나 새 센서가 추가돼도 프로그램을 고치지 않고 설정만 바꿔 대응한다.

**Why this priority**: 과제 산출물("형식 변경 상황 하나를 가정하고 무엇을 바꿨는지 기록")이다.

**Independent Test**: 형식이 바뀐 가상 메시지를 보내고, 설정만 고쳐서 저장되는지 본다.

---

### Edge Cases (과제 "생각해 볼 점" — 답은 미정)

- 시각은 센서가 찍은 것과 수신한 것 중 무엇을 저장하나? 네트워크가 30초 밀렸다가 한꺼번에 도착하면? → **미정**
- 수집과 학습·추론이 같은 저장소를 동시에 쓰면 어떤 문제가 생기나? → **미정**
- 같은 메시지가 두 번 오면(재전송)? (심화 B) → **미정**
- 형식이 맞지 않는 메시지, 저장소가 잠시 안 될 때의 처리 → **미정**

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 수집기는 MQTT 브로커 `data.withio.net:1883`을 아이디·비밀번호로 구독한다. (aip-1에서 `mosquitto_sub`로 접속 확인함) [NEEDS CLARIFICATION: 토픽 구조, 메시지 형식]
- **FR-002**: 각 값은 공간, 항목(co2/temperature/humidity), 시각과 함께 저장한다.
- **FR-003**: 메시지 형식 변경·센서 추가는 설정만 바꿔 대응한다.
- **FR-004**: 브로커 연결이 끊기면 자동으로 재접속한다.
- **FR-005**: 보드 부팅 시 수집기가 자동으로 시작된다.
- **FR-006**: 공간·항목별 건수, 마지막 수신 시각, 커버율, 결측 구간을 확인할 수 있다.
- **FR-007**: 접속 비밀번호·토큰은 저장소(git)에 올리지 않는다.
- **FR-008**: 저장소는 Jetson(aip-1)에 설치한 InfluxDB 2.x를 쓴다. 서버는 하나, 계정·org·버킷은 사람마다 따로 둔다.
- **FR-009**: 수집기는 Telegraf로 구성한다. 사람마다 자기 버킷에 쓰고, MQTT client ID는 사람마다 다르게 한다.

### Key Entities

- **측정값**: 공간, 항목, 값, 단위, 시각
- **공간**: 강의실 2개, 회의실, 라운지 [NEEDS CLARIFICATION: 메시지 안의 실제 이름]

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 브로커를 껐다 켜도 1분 안에 수집이 다시 시작된다.
- **SC-002**: 보드를 재부팅해도 수집이 자동으로 다시 시작된다.
- **SC-003**: 24시간 커버율 95% 이상. 빠진 구간은 원인을 설명할 수 있다.
- **SC-004**: 메시지 형식 변경 1건을 설정 수정만으로 대응한 기록이 있다.

## Assumptions

- 개인 과제로 진행한다. Jetson aip-1을 여러 사람이 계정을 나눠 같이 쓴다.
- Jetson에 프로그램을 설치할 때는 무엇인지, 왜 필요한지, 안 깔아도 되는 경우를 함께 기록한다.
