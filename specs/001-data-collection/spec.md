# Feature Specification: 데이터 수집 체계 (과제 1)

**Feature Branch**: `001-data-collection`

**Created**: 2026-10-20 | **Updated**: 2026-10-21

**Status**: Draft

**Input**: 과제 안내문 "과제 1. 데이터 수집 체계" — MQTT로 1분마다 들어오는 CO₂·온도·습도 메시지를 받아
공간·항목·시각별로 저장하는 수집기를 Jetson에서 상시 가동한다.

**이 과제를 하는 방식**: MQTT 메시지는 운영진이 이미 InfluxDB(`iot-bucket`)에 쌓고 있고,
운영진에게 MQTT를 직접 받지 않고 이 DB에서 가져와도 된다고 확인했다.
그래서 "수집기"는 **운영진 InfluxDB에서 필요한 데이터만 골라 aip-1의 내 InfluxDB 버킷으로 옮기는 프로그램**이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 필요한 데이터만 골라 내 버킷에 저장한다 (Priority: P1) 🎯 MVP

옮기기 프로그램을 실행하면, 운영진 InfluxDB의 실습실·회의실 CO₂·온도·습도 값이 공간·장치·항목·시각별로 내 버킷에 쌓인다.

**Why this priority**: 데이터가 없으면 과제 2~8 모두 시작할 수 없다.

**Independent Test**: 프로그램을 10분 돌린 뒤 내 버킷을 조회해, 운영진 DB의 같은 기간 값과 건수가 같은지 본다.

**Acceptance Scenarios**:

1. **Given** 운영진 DB에 새 값이 들어오는 중, **When** 프로그램을 실행하면, **Then** 다음 실행 주기 안에 내 버킷에 그 값이 보인다.

---

### User Story 2 - 사람 손 없이 다시 살아난다 (Priority: P1)

운영진 DB 접속이 끊기거나 보드가 재부팅돼도 옮기기가 자동으로 다시 시작되고, 끊긴 동안의 값도 채워진다.

**Why this priority**: 하루만 멈춰도 그날 데이터는 학습·평가에 못 쓴다.

**Independent Test**: 옮기는 중 네트워크를 끊었다 다시 연결하고, 보드를 재부팅한 뒤 재개되는지와 빠진 구간이 채워졌는지 본다.

**Acceptance Scenarios**:

1. **Given** 옮기는 중, **When** 운영진 DB 접속이 끊겼다 돌아오면, **Then** 자동으로 재개되고 끊긴 동안의 값도 내 버킷에 들어온다.
2. **Given** 프로그램이 서비스로 등록된 보드, **When** 재부팅하면, **Then** 로그인 없이 자동으로 시작된다.

---

### User Story 3 - 수집 현황을 한눈에 본다 (Priority: P2)

"지금 데이터가 잘 쌓이고 있는가"를 확인한다.

**Why this priority**: 멈춘 것을 빨리 알아야 고칠 수 있고, 커버율 보고가 산출물이다.

**Independent Test**: 공간·장치·항목별 건수, 마지막 수신 시각, 24시간 커버율, 결측 구간이 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 24시간 쌓인 데이터, **When** 현황을 조회하면, **Then** 장치별 커버율이 표로 나온다. 커버율은 1분 칸이 아니라 장치마다 자기 전송 간격 기준으로 잰다. (칸 크기 = 장치의 보고 간격 중앙값 × 2)
2. **Given** 빠진 구간, **When** 현황을 조회하면, **Then** 결측 구간의 시작·끝 시각을 알 수 있다.

---

### User Story 4 - 형식이 바뀌어도 설정만 고친다 (Priority: P2)

공간 이름이 바뀌거나 장치·항목이 추가돼도 프로그램을 고치지 않고 설정만 바꿔 대응한다.

**Why this priority**: 과제 산출물("형식 변경 상황 하나를 가정하고 무엇을 바꿨는지 기록")이다.

**Independent Test**: 형식 변경 상황 하나를 가정하고, 설정만 고쳐서 계속 저장되는지 본다.

---

### Edge Cases (과제 "생각해 볼 점" — 답은 미정)

- 시각은 운영진 DB에 찍힌 `_time`을 그대로 쓴다. 이 시각이 센서 시각인지 수신 시각인지는 → **미정**(운영진 확인)
- 수집과 학습·추론이 같은 저장소를 동시에 쓰면 어떤 문제가 생기나? → **미정**
- 같은 값이 두 번 들어온 경우(약 2ms 간격 재전송을 실제로 봄) (심화 B) → 내 쪽에서 겹쳐 다시 쓰는 것은 덮어쓰기라 중복 없음(확인). 원본의 ms 차이 재전송은 **미정**
- 운영진 DB가 잠시 안 될 때, 내 InfluxDB가 잠시 안 될 때의 처리 → 실패를 기록하고 진행 위치를 그대로 둔다. 다음 실행(1분 뒤)이 같은 지점부터 다시 가져온다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 원본은 운영진 InfluxDB(`https://influx.java21.net` 또는 내부망 `http://10.116.64.13:8086`, 버킷 `iot-bucket`)다. 받은 토큰으로 읽기만 하고, 운영진 DB에는 쓰지 않는다.
- **FR-002**: 가져올 데이터: `location`이 `실습실`·`회의실`이고 `_measurement`가 `co2`·`temperature`·`humidity`인 값, 모든 장치.
- **FR-003**: 저장할 때 `location`, `device_id`, `point` 태그와 항목, 값, 시각을 유지한다. (`spot`은 `point`와 같은 뜻이라 뺀다)
- **FR-004**: 가져올 공간·항목 목록은 설정으로 둔다. 바뀌면 설정만 고친다.
- **FR-005**: 접속이 끊겼다 돌아오면 자동으로 재개하고, 빠진 구간을 다시 가져온다.
- **FR-006**: 보드 부팅 시 옮기기 프로그램이 자동으로 시작된다.
- **FR-007**: 장치별 건수, 마지막 수신 시각, 커버율, 결측 구간을 확인할 수 있다.
- **FR-008**: 토큰은 저장소(git)에 올리지 않는다. 각자 홈 폴더의 본인만 읽을 수 있는 파일에 둔다.
- **FR-009**: 저장소는 aip-1에 설치한 InfluxDB 2.x 하나. org 1개, 사람마다 버킷 1개(`jiwon`, `seohyun`), 자기 버킷만 읽고 쓰는 토큰 1개.
- **FR-010**: 옮기는 방법은 Python 스크립트 + systemd timer(1분마다)

### Key Entities

- **측정값**: 공간(location), 장치(device_id), 자리(point), 항목, 값, 시각
- **공간**: 실습실(안내문의 "강의실"), 회의실

### 안내문과 실제 데이터의 차이 (보고서에 적을 것)

| 안내문 | 실제 (2026-10-21 조회) |
|---|---|
| 강의실 2개, 회의실, 라운지 | 공간 이름은 사무실·사무실 밖·실습실·창고·회의실. 강의실 = 실습실 |
| 강의실 2개 | 실습실은 한 방에 센서 8개(CO₂·온도·습도 4개, 온도·습도만 4개, 그중 1개는 복도) |
| 회의실 | 센서 1개 |
| 1분마다 | 장치마다 약 1분·2분·10분으로 다름 (회의실은 약 10분) |
| — | `point`와 `spot` 태그가 같은 뜻인데 표기가 다름 (예: 후방 오른쪽 / 후방 우측) |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영진 DB 접속이 끊겼다 돌아오면 자동으로 재개되고, 빠진 구간이 채워진다.
- **SC-002**: 보드를 재부팅해도 자동으로 다시 시작된다.
- **SC-003**: 24시간 커버율 95% 이상(장치별 자기 간격 기준). 빠진 구간은 원인을 설명할 수 있다.
- **SC-004**: 형식 변경 1건을 설정 수정만으로 대응한 기록이 있다.

## Assumptions

- 개인 과제로 진행한다. Jetson aip-1을 여러 사람이 계정을 나눠 같이 쓴다.
- Jetson에 프로그램을 설치할 때는 무엇인지, 왜 필요한지, 안 깔아도 되는 경우를 함께 기록한다.
