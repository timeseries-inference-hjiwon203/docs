# Feature Specification: 데이터 수집 체계 (과제 1)

**Feature Branch**: `001-data-collection`

**Created**: 2026-10-20

**Status**: Draft

**Input**: 과제 안내문 "과제 1. 데이터 수집 체계" — MQTT로 1분마다 들어오는 CO₂·온도·습도 메시지를 받아
공간·항목·시각별로 저장하는 수집기를 Jetson에서 상시 가동한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 센서 메시지를 받아 저장한다 (Priority: P1) 🎯 MVP

팀원이 수집기를 실행하면, MQTT 브로커에서 들어오는 센서 메시지가 공간·항목·시각별로 시계열 저장소에 쌓인다.

**Why this priority**: 데이터가 없으면 과제 2~8 모두 시작할 수 없다.

**Independent Test**: 수집기를 10분 돌린 뒤 저장소를 조회해, 4개 공간 × 3개 항목에 1분 간격으로 값이 쌓였는지 본다.

**Acceptance Scenarios**:

1. **Given** 브로커가 메시지를 보내는 중, **When** 수집기를 실행하면, **Then** 1분 안에 저장소에 첫 값이 보인다.
2. **Given** 0ppm 같은 깨진 값이 들어오면, **When** 저장할 때, **Then** 원본 그대로 저장하되 버리지 않는다(정제는 과제 2에서).

---

### User Story 2 - 사람 손 없이 다시 살아난다 (Priority: P1)

브로커가 재시작되거나 네트워크가 끊기거나 보드가 재부팅돼도 수집이 자동으로 다시 시작된다.

**Why this priority**: 하루만 멈춰도 그날 데이터는 학습·평가에 못 쓴다.

**Independent Test**: 수집 중 브로커를 끊었다 다시 연결하고, 보드를 재부팅한 뒤 수집이 재개되는지 본다.

**Acceptance Scenarios**:

1. **Given** 수집 중, **When** 브로커를 껐다 켜면, **Then** 1분 안에 수집이 다시 시작된다.
2. **Given** 수집기가 등록된 보드, **When** 재부팅하면, **Then** 로그인 없이 수집이 자동으로 시작된다.

---

### User Story 3 - 수집 현황을 한눈에 본다 (Priority: P2)

팀원이 명령 하나로 "지금 데이터가 잘 쌓이고 있는가"를 확인한다.

**Why this priority**: 멈춘 것을 빨리 알아야 고칠 수 있고, 커버율 보고가 산출물이다.

**Independent Test**: 현황 명령을 실행해 공간·항목별 건수, 마지막 수신 시각, 24시간 커버율 표가 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 24시간 수집된 데이터, **When** 현황을 조회하면, **Then** 공간·항목별 커버율(1분 칸 중 값이 있는 비율)이 표로 나온다.
2. **Given** 30분 동안 빠진 구간, **When** 현황을 조회하면, **Then** 결측 구간의 시작·끝 시각이 함께 나온다.

---

### User Story 4 - 형식이 바뀌어도 설정만 고친다 (Priority: P2)

메시지 형식이 바뀌거나 새 센서가 추가돼도 코드를 고치지 않고 설정 파일만 바꿔 대응한다.

**Why this priority**: 과제 산출물("형식 변경 상황 하나를 가정하고 무엇을 바꿨는지 기록")이자 원칙 VI.

**Independent Test**: 필드 이름이 바뀐 가상 메시지를 보내고, 설정 파일만 고쳐서 저장되는지 본다.

**Acceptance Scenarios**:

1. **Given** `co2` 필드가 `CO2_ppm`으로 바뀐 메시지, **When** 설정 파일의 필드 매핑만 고치면, **Then** 코드 수정 없이 저장된다.

---

### Edge Cases

- 네트워크가 30초 밀렸다가 메시지가 한꺼번에 도착하면? → 센서 시각과 수신 시각을 둘 다 저장해 구분한다.
- 같은 메시지가 두 번 오면(재전송)? → 같은 공간·항목·센서 시각이면 덮어써서 중복이 생기지 않게 한다(심화 B).
- 형식이 맞지 않는 메시지가 오면? → 수집기는 멈추지 않고 건너뛰며 로그에 남긴다.
- 저장소(InfluxDB)가 잠시 안 되면? → 메모리/로컬 파일에 잠시 쌓았다가 다시 보낸다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 수집기는 MQTT 브로커의 센서 토픽을 구독해야 한다. [NEEDS CLARIFICATION: 브로커 주소·포트·토픽 구조·인증 — README 확인]
- **FR-002**: 각 값은 공간, 항목(co2/temperature/humidity), 센서 시각, 수신 시각과 함께 저장해야 한다.
- **FR-003**: 토픽→공간, 필드→항목 매핑은 설정 파일로 정의해야 한다.
- **FR-004**: 브로커 연결이 끊기면 자동으로 재접속해야 한다.
- **FR-005**: 보드 부팅 시 수집기가 자동으로 시작되어야 한다.
- **FR-006**: 공간·항목별 건수, 마지막 수신 시각, 커버율, 결측 구간을 보여 주는 현황 명령이 있어야 한다.
- **FR-007**: 접속 토큰·비밀번호는 코드와 저장소에 넣지 않는다.
- **FR-008**: 저장소는 InfluxDB(`data.withio.net:8086`)를 쓴다. [NEEDS CLARIFICATION: 버전, org, bucket, 접속 가능한 네트워크]

### Key Entities

- **측정값(Measurement point)**: 공간, 항목, 값, 단위, 센서 시각, 수신 시각
- **공간(Space)**: 강의실1, 강의실2, 회의실, 라운지
- **수집 설정(Mapping config)**: 토픽 패턴, 필드 이름 매핑, 시각 필드, 단위

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 브로커를 껐다 켜도 1분 안에 수집이 다시 시작된다.
- **SC-002**: 보드를 재부팅해도 수집이 자동으로 다시 시작된다.
- **SC-003**: 24시간 커버율 95% 이상. 빠진 구간은 원인을 설명할 수 있다.
- **SC-004**: 메시지 형식 변경 1건을 설정 파일 수정만으로 대응한 기록이 있다.

## Assumptions

- 실데이터가 3주 쌓이기 전에는 제공된 합성 데이터 생성기로 MQTT 메시지를 흉내 낸다.
- InfluxDB는 운영진이 제공한 것을 쓴다. 팀 Jetson에서 직접 띄우지 않는다(접속이 안 되면 Jetson에 로컬 InfluxDB를 띄우는 것을 대안으로 둔다).
- 심화(B) 항목(1년 뒤 용량 추정·보관 정책, 재전송 중복 처리)은 기본 기능이 끝난 뒤 한다.
