이후 모델이 넘어야 할 기준선(현재값 유지, 최근 1시간 평균, 어제 같은 시각)의 성능을 잰다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 정제 규칙을 정한다 (Priority: P1) 🎯 MVP

아래 각각을 어떻게 처리할지 정하고 이유를 쓴다.

- 물리적으로 불가능한 값(0ppm, 60℃ 등)
- 짧은 결측(몇 분)과 긴 결측(몇 시간)
- 센서마다 다른 기록 주기
- (우리 데이터 사정) 한 공간에 센서가 여러 개일 때 공간 값을 어떻게 만들지, 원본 재전송 중복

**Why this priority**: 정제가 안 된 데이터로 잰 기준선·모델 점수는 믿을 수 없다. 과제 8 서비스도 같은 규칙을 쓴다.

**Independent Test**: 정제 전후 건수와 제거된 값 수가 공간·항목별로 표로 나온다.

**Acceptance Scenarios**:

1. **Given** 원본 데이터, **When** 정제 규칙을 적용하면, **Then** 공간·항목별 제거된 값 수와 이유별 건수가 나온다.
2. **Given** 같은 원본, **When** 다시 적용하면, **Then** 같은 결과가 나온다(규칙이 코드로 고정돼 있다).

---

### User Story 2 - 분석 간격과 기간 분할을 정한다 (Priority: P1)

- 1분 그대로 쓸지, 몇 분 단위로 모을지 정하고 근거를 쓴다
- 학습·검증·시험 기간을 시간 순서로 나누고, 무작위로 섞으면 안 되는 이유를 쓴다

**Why this priority**: 과제 3~6이 같은 간격·같은 분할을 써야 공정하게 비교된다.

**Independent Test**: 분할 경계 날짜와 각 기간의 건수가 표로 나온다.

---

### User Story 3 - 데이터를 진단한다 (Priority: P2)

- 공간별·항목별 결측률과 제거된 이상값 수
- 평일 시간대별 평균 패턴(수업·점심·퇴실이 보이는가)
- 수업 시작·점심·퇴실 뒤 CO₂가 몇 분 만에 반응하는가, 일정과 실제 CO₂ 변화가 어긋나는 날은 언제인가

**Independent Test**: 결측률 표, 평일 시간대별 평균 그래프, 일정–CO₂ 반응 시간 표가 나온다.

---

### User Story 4 - 기준선 3가지의 성능을 잰다 (Priority: P1)

현재값 유지, 최근 1시간 평균, 어제 같은 시각 — 5·15·30·60분 뒤 CO₂·온도 오차(MAE)를 비교한다.

**Why this priority**: 과제 3의 확인 기준("현재값 유지보다 30% 이상 작다")이 이 표를 기준으로 한다.

**Independent Test**: 기준선 3종 × 4시점 × CO₂·온도 × 공간 MAE 표가 나온다.

---

### Edge Cases (과제 "생각해 볼 점" — 답은 진단서에)

- '어제 같은 시각'이 가장 약한 이유는? 어떤 공간이라면 이 방법이 강할까? → 답은 report.md 5절
- 고장이 섞인 구간은 학습에 넣어야 할까, 빼야 할까? 평가에서는? → 학습·평가 모두 뺀다. 답은 report.md 5절
- 실습실은 24시간 자율 사용이라 수업 시간 밖에도 사람이 있을 수 있다 → 일정과 CO₂가 어긋나는 날 분석에 반영
- 원본에 값이 없는 기간(2025-08-15 ~ 09-02)이 분할 경계나 '어제 같은 시각'에 걸릴 때 → 분석 시작을 2025-09-03으로 정해서 이 기간은 쓰지 않는다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 데이터는 과제 1에서 aip-1 InfluxDB(org `aip-1`, 버킷 `jiwon`)에 쌓은 실데이터를 읽기만 한다. 공간 `실습실`(= 안내문의 강의실), `회의실` × `co2`·`temperature`·`humidity`, 2025-08-08 ~.
- **FR-002**: 분석은 지원의 Mac에서 한다. Mac이 Tailscale로 aip-1 InfluxDB를 직접 읽는다. Jetson에는 아무것도 설치하지 않는다.
- **FR-003**: 정제 규칙은 과제 8 서비스(Jetson)에서도 똑같이 쓸 수 있도록 따로 떼어 둔다.
- **FR-004**: 정규화(평균·표준편차)는 학습 기간 데이터로만 계산한다.
- **FR-005**: 기준선을 평가한 시점 목록을 남겨, 과제 3·6에서 같은 시점으로 평가한다.
- **FR-006**: 모든 결과표에 측정 조건(데이터 기간, 실데이터, 시험 기간)을 적는다.
- **FR-007**: 토큰은 git에 올리지 않는다.

### 정할 것

- 분석 간격 → 2026-10-22 결정: 5분
- 실습실 센서 합치기 → 2026-10-22 결정: 2025-09-03부터 있던 4개 센서의 5분 칸 값 중앙값(전체 7개와 차이 온도 0.07℃, 습도 0.5%)
- 학습·검증·시험 기간 → 2026-10-22 결정: 학습 2025-09-03~2026-08-31, 검증 2026-09, 시험 2026-10-01~10-21 (시험은 17명 시기 = 서비스 조건)
- 불가능한 값의 범위 → 2026-10-22 결정: CO₂ 350ppm 미만·10,000ppm 이상, 습도 0~100% 밖, 온도 0℃ 이하 제거
- 같은 센서·같은 시각 기록 중 하나라도 범위 밖이면 그 시각 기록 전부 버림 (2026-10-22 결정)
- 결측 처리 → 2026-10-22 결정: 15분(3칸)까지 앞 값으로 채움, 더 길면 비움. 채운 칸은 채점에서 뺌(real_* 표시)
- 원본 재전송 → 2026-10-22 결정: 같은 센서·항목·값이 1초 안에 다시 오면 뒤의 것을 버린다
- 사용 기간 → 2026-10-22 결정: 2025-09-03부터 (그 전은 device_id 없음)
- 복도 센서 → 2026-10-22 결정: `24e124136d151523`(point=복도)은 실습실 값에서 뺀다

### Key Entities

- **측정값**: 공간(location), 장치(device_id), 자리(point), 항목, 값, 시각
- **일정**: 수업 시간표(평일 09:00~18:00, 점심 11:30~13:00, 공휴일 제외). 회의실 예약 자료는 없음
- **실습실 이용자 수**: 2025-12 말 ~ 2026-09 말 45~50명, 2026-10-01 ~ 11-27 약 17명 (그 전은 모름)

### 이미 알고 있는 데이터 사정 (과제 1 보고서)

| 사정 | 영향 |
|---|---|
| 원본에도 없는 구간 2025-08-15 ~ 2025-09-02 | 결측률·분할에 반영 |
| `device_id` 태그는 2025-09-03부터, `point` 태그는 2026-08-11 무렵부터 | 그 전은 장치 구분이 안 됨 |
| 보고 주기: 실습실 1분·2분·10분 섞임, 회의실 약 10분 | 분석 간격 결정에 반영 |
| 실습실 센서 여러 개(co2 4개, 온도·습도 8개, 2026-08에 늘어남, 1개는 복도), 회의실 항목마다 1개 | 공간 값 만드는 방법 결정에 반영 |
| 원본 재전송(약 2ms 차이 같은 값) | 정제 규칙에 반영 |
| 1년 치를 한 번에 읽으면 60초가 넘음 | 나눠 읽기 |

## Success Criteria *(mandatory)*

### Measurable Outcomes (안내문 확인 기준 그대로)

- **SC-001**: 정규화(평균·표준편차) 값을 학습 기간 데이터로만 계산했다
- **SC-002**: 기준선 평가와 이후 모델 평가가 같은 시점, 같은 조건에서 이루어진다
- **SC-003**: 세 기준선 중 무엇이 가장 강한지, 그 이유를 설명한다

### 산출물

- 데이터 진단서(1~2쪽): 정제 규칙, 분할 기준, 패턴 그래프, 일정–CO₂ 반응 분석
- 기준선 성능표

## Assumptions

- 개인 과제로 진행한다.
- 회의실은 예약 자료가 없어 일정–CO₂ 반응 분석은 실습실만 한다. 회의실은 패턴만 본다.
